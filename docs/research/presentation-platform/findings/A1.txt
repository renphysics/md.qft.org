##### A1-audit-player

SUMMARY:
The player accepts exactly one thing: a `qft-presentation.json` v1 manifest (engine must be "slidev") plus one self-contained HTML. Standard Reveal.js ZIPs, ordinary Slidev dist ZIPs and Slidev source are refused, or misrouted to the Markdown importer; nothing is editable.

The blockers are mostly incidental. A hand-inlined Reveal.js 6.0.2 deck plays unmodified in 376 ms, so the sandbox is already engine-agnostic. What blocks the goal is the manifest gate, the single-HTML rule, the blob: document URL (breaks routers and fragment links), fatal-on-any-error, and an immutable package model.

Security, tested with ~75 hostile probes in Chromium 158:
- **Editor isolation holds.** No probe reached drafts, storage, DOM, top navigation, popups or dialogs.
- **"No network" does not hold.** A script-inserted `<link rel=prerender>` makes a real HTTP GET to any URL, and WebRTC sends STUN packets. Neither raises a CSP violation, and no CSP variant I tried stops the prerender request.
- **Error reporting is advisory.** The package can read its nonce and token, mute violation reports, and forge host messages.
- **Infinite loops** are survivable on desktop Chromium (Stop in 43 ms) but freeze the editor where sandboxed frames share a process.

Two findings matter most for the redesign:
- A same-origin service worker cannot serve an opaque sandboxed frame, and runner-created blob URLs fail in the child. Blobs posted into the child and turned into blob URLs there work for images, CSS, classic scripts, ES modules, fetch, import() and workers.
- In full Chromium (headed too), arrow keys do not reach the deck after Start until the user clicks; a small repair is verified.

Only Chromium was available; Firefox and Safari behaviour is inferred or unknown.

RECOMMENDATIONS (9):

[R1] (effort S; impact high) Keep the double opaque-origin sandbox and typed message protocol; reword the network promise
   WHY: Every probe against editor data failed, so the runner -> blob child structure, the editor CSP and the archive validator are worth keeping as the base for any redesign. The network block is a privacy default, not a guarantee: prerender and WebRTC get out in Chromium 158 and no declarative control exists. UI and README text should say that decks cannot read drafts, rather than that playback has no external connections.
   RISKS: If the product needs a hard no-network guarantee against hostile decks, iframe sandbox plus CSP cannot deliver it in Chromium today.

[R2] (effort M; impact high) Open the import gate: classify archives and make the manifest optional
   WHY: The manifest requirement and the engine constant are the first thing that rejects every standard Reveal.js or Slidev ZIP, and the fall-through sends some of them to the Markdown importer. Returning an archive kind instead of throwing at presentation-package.ts:323 and :328, synthesising a manifest (entry = shallowest index.html, engine detected from content) and widening the engine type in package, store and schema removes that blocker and the misleading messages.
   RISKS: Heuristic detection can misclassify; the store's validateInfo must change in the same release or old records and new records will not list together.

[R3] (effort M; impact high) Add an in-editor linker for classic multi-file sites as the first Reveal.js step
   WHY: Text inlining of stylesheets and classic scripts plus data: URIs for assets yields a single HTML that the existing player runs unchanged (818 KB Reveal deck, 376 ms). It needs no runtime or CSP change and reuses the existing export. The repo packer is not suitable because it bundles UMD scripts as modules.
   RISKS: The 24 MiB HTML cap with 1.33x base64 growth limits media; ES modules, run-time relative URLs and CDN references are not covered; Reveal F/S keys and lazy data-src still need the error-policy and shim work.

[R4] (effort L; impact high) Build the virtual file system by transferring Blobs into the child and creating blob: URLs there
   WHY: This is the only route found that keeps the opaque sandbox: service workers cannot reach it and runner-created blob URLs fail, while child-created ones work for images, CSS, classic and module scripts, fetch, import() and workers. It needs blob: added to the two policies, a loader document, reference rewriting, and shims for history, fragment links and relative fetches. It is the prerequisite for ordinary Slidev dist output and large media.
   RISKS: Verified in Chromium only. Module specifier rewriting and router emulation for Slidev are the hard parts; the blob: URL limits remain and must be shimmed.

[R5] (effort M; impact high) Make runtime errors non-fatal by default and move supervision into the runner
   WHY: Killing the deck on any error breaks mainstream decks (Reveal F and S keys, one bad image, a web-font import) and is trivially evaded by a hostile package anyway. Report errors in an overlay and keep the frame. Let the runner count child load events to detect a deck replacing its document, add a message-rate limit, and prefix deck-supplied text in the host notice. Show failures inside the fullscreen element.
   RISKS: A misbehaving deck keeps running until the user stops it; the navigation watchdog leaves a window of a few milliseconds.

[R6] (effort S; impact high) Fix the keyboard focus hand-off and run the browser test in full Chromium
   WHY: Arrow keys do nothing after Start or Present in real Chromium, which is the first thing a presenter tries. The repair is three lines: blur() then focus() the outer iframe after ready, then send the existing focus message. Running tests/browser/presentations.mjs with channel 'chromium' and without the pre-click would have caught it.
   RISKS: Confirmed in headless and headed Chromium under Playwright's emulated window focus; a manual check on a physical desktop is still advisable.

[R7] (effort S; impact medium) Grant low-risk capabilities and stop altering the deck's document
   WHY: allow-forms with form-action 'none' kept restores JS forms; consider allow-modals, fullscreen delegation and clipboard-write. Drop the injected box-sizing rule, keep title, body id and viewport, and replace the rootAttributes regex with parsed attributes. None of these crosses the origin boundary, and each removes a silent failure seen in testing.
   RISKS: allow-modals lets a deck block the tab with dialogs; fullscreen delegation lets a deck enter fullscreen on a user gesture.

[R8] (effort L; impact high) Introduce an editable project model on top of the existing store and player
   WHY: Editing needs a project object with a file map, an update operation in the store (database version 2, optionally an edits overlay so autosave does not rewrite a 60 MiB ZIP), a player update(html) method and slide-position hand-over across restarts. CodeMirror with HTML, CSS and JS modes is already installed. For Reveal.js and plain HTML decks the source is the playable artifact, so this delivers live editing without a compiler.
   RISKS: Slidev source editing additionally needs an in-browser compile step, which is outside the player. WebAssembly tooling must run in a same-origin network worker or the editor CSP needs 'wasm-unsafe-eval'.

[R9] (effort S; impact medium) Validate playability at import and de-duplicate saved packages
   WHY: Running the inert prepare step before saving turns four save-then-fail cases into immediate, actionable messages. A content hash stops the library growing by 1.6 MB on every example click or deep-link visit.
   RISKS: Prepare at import adds parse time for large packages (under 2 s at the 24 MiB limit).

OPEN QUESTIONS:
 - Firefox and Safari were not available: do the prerender request, the WebRTC packets, the focus hand-off bug, the fragment-navigation block and the child-created blob URL file system behave the same there?
 - The HTML Standard lets a sandboxed frame navigate a non-top ancestor; Chromium blocks it. Do other engines allow the deck to navigate the runner frame (the editor's frame-src 'self' would limit it to same-origin URLs)?
 - Does Chrome's user setting "Preload pages: off" suppress the <link rel=prerender> request, and do preconnect and dns-prefetch leak? Playwright starts Chromium with --disable-background-networking, so these could not be observed.
 - Is WebAssembly in a same-origin network worker also allowed under the editor's meta CSP in Firefox and Safari, or must 'wasm-unsafe-eval' be added?
 - Does a tab hidden during loading cause a false "has not finished loading" error? The ready signal needs two animation frames; headless Chromium keeps pages visible, so this is inferred from code only.
 - How does the player behave on Android Chrome and Firefox when a deck loops forever? Same-process sandboxed frames are documented or inferred there, but not tested.
 - Is a hard no-network guarantee a product requirement, or is "decks cannot read your drafts" enough? The answer decides whether CDN-based decks may be allowed to load their libraries.
 - Memory exhaustion by a package was not tested because the machine is shared.
