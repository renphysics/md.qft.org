##### B6-editor-ux

SUMMARY:
Keep CodeMirror 6. The site's bundle already contains the HTML/CSS/JS parsers, so JSON, YAML, Vue, lint, merge review, slide mapping and an AI-answer importer add +61.5 KB min / +23.2 KB gzip, against 2,833 KB / 729 KB gzip plus workers for Monaco's smallest core (and no mobile support).

Slide-aware editing is feasible and cheap. A 5 KB mapper on the Lezer HTML parser matched 41/41 slides of Reveal's demo deck and 12/12 of a mixed HTML/Markdown deck. Reveal's own postMessage API syncs slides across the opaque sandbox with no injected code. A built Slidev client exposes the current slide through vue-router, and a port of Slidev's splitter matches the official parser.

Full reload is fast enough to be the default refresh: median 173–189 ms for 41 slides, 482 ms for 120 slides with 360 formulas, about 210 ms for a compiled Slidev deck. Loading the new frame hidden and swapping when ready removes flashing and keeps the last good render.

A dependency-free 3.2 KB importer handled 13/13 synthetic chat-answer shapes (my own samples) and refused an elided file; strict jsdiff threw on a sloppy diff.

Blocking issue found: a Reveal deck with `hash: true` is killed by the real production player, because a SecurityError from `replaceState` is treated as fatal. A six-line shim fixes it.

File System Access remains Chromium-only. WebMCP is in origin trial as `document.modelContext`. The Prompt API is stable in desktop Chrome 148.

Not tested: real screen readers and phones, Firefox/Safari, the folder picker end to end.

RECOMMENDATIONS (13):

[R1] (effort S; impact high) Add a history shim to the sandbox bootstrap and stop treating every script error as fatal while previewing
   WHY: Verified in the real production player: a Reveal deck with `hash: true` ends in "Playback needs attention"; wrapping history.replaceState/pushState in try/catch makes it play. During editing, transient errors must be reported without tearing the frame down; only "never became ready" should discard a candidate.
   RISKS: Relaxing the fatal-error rule for normal playback changes a deliberate safety choice; it could be limited to edit mode.

[R2] (effort S; impact high) Keep CodeMirror 6 and load the extra languages and merge view in a lazy project-editor chunk
   WHY: HTML/CSS/JS are already in the bundle; the full set costs +23.2 KB gzip against 729 KB gzip plus workers for Monaco, and CodeMirror works on phones. Its Lezer trees also power the slide mapping.
   RISKS: @codemirror/lang-vue is 0.1.3 and unmaintained since 2023; it gives highlighting, not Vue type checking.

[R3] (effort M; impact high) Build the project model as immutable original ZIP + overlay + project journal + named snapshots, with ZIP export
   WHY: The presentation store already keeps the upload as a Blob, so "restore original" is free; an overlay makes snapshots cheap; a journal gives one-click undo for multi-file operations that CodeMirror's per-file history cannot provide.
   RISKS: Best-effort browser storage and Safari's seven-day rule: show where work lives and keep Download ZIP one click away; run fflate off the main thread (661 ms synchronous for 4.9 MB).

[R4] (effort M; impact high) Make the editor slide-first: slide list by default, file tree behind a toggle, framework files collapsed and read-only
   WHY: The audience thinks in slides; a Reveal ZIP is 48+ files of which a handful are content. Slidev's tree view, slides.com's per-slide HTML editor and Sandpack's readOnly/hidden flags all point the same way.
   RISKS: Misclassifying a file as framework hides something the teacher needs; provide "show all files".

[R5] (effort M; impact high) Refresh by double-buffered full reload with slide restore; add CSS swap and single-slide patch later
   WHY: Measured 0.17–0.48 s for reload and 25–37 ms for patches; the hidden-frame swap removes flashing and is also the "last good render" mechanism. In-place Markdown re-rendering is not worth building.
   RISKS: Two live copies briefly double memory and could double-play audio/video; interactive demo state is lost on reload, so pause auto-refresh while the user is interacting with a slide.

[R6] (effort M; impact high) Implement slide ↔ source sync with the Lezer mapper, Reveal's postMessage API and a vue-router bridge for Slidev, and verify the map against the runtime after every reload
   WHY: 41/41 and 12/12 slides mapped; zero-injection sync works for Reveal. Malformed HTML makes the static map and the browser disagree (34 versus 42), so compare and say "approximate" instead of jumping to the wrong place.
   RISKS: The Slidev bridge relies on `__vue_app__` and vue-router internals rather than a public Slidev API; the runner relay needs a new whitelisted message kind.

[R7] (effort M; impact high) Ship the AI loop as copy-out context packs plus a paste-in importer with merge-view review
   WHY: No accounts or keys; the importer prototype is 3.2 KB gzip and tolerant of real chat sloppiness, while a strict patch library fails. The site writes the prompt, so it can ask for SEARCH/REPLACE blocks with a file path line.
   RISKS: Format compliance by current models is unmeasured; wrong-place application must stay behind review, with placeholder refusal, shrink warnings and single-step undo.

[R8] (effort S; impact high) Do not offer an editor for files whose edits cannot change playback
   WHY: Today a portable Slidev package plays a compiled copy; editing its source/ changes nothing. Until a compile path exists, keep those files read-only with an explicit banner.
   RISKS: Users may expect editing anyway; the banner must say what to do instead.

[R9] (effort M; impact medium) Add a slide inspector (title, notes, background, transition, hidden) and slide operations as source edits
   WHY: A form is the safe middle ground for non-developers and works for Markdown and Slidev content that has no HTML source element to click. Each control is an attribute or range replacement of the kind already verified for text write-back.
   RISKS: Three source dialects (Reveal HTML, Reveal Markdown, Slidev frontmatter) triple the cases; start with Reveal HTML.

[R10] (effort M; impact medium) Deliver assets to the sandbox as transferred bytes turned into blobs inside the frame
   WHY: Parent blob URLs are blocked in the opaque frame; base64 inflates media by a third against a 24 MB HTML limit; a 50 MB transfer took 0.1 ms. It also enables replacing an image without a reload.
   RISKS: Requires URL rewriting inside the frame for src, CSS url() and scripted loads; scripted fetches of relative paths still fail.

[R11] (effort L; impact medium) Offer real-folder editing as a Chromium-only enhancement with folder import as the universal fallback
   WHY: showDirectoryPicker, stored permissions and FileSystemObserver give edit-in-VS-Code-and-watch without ZIP round trips, but Firefox and Safari oppose the API. input webkitdirectory and folder drop work everywhere for import.
   RISKS: Not tested end to end here; external and local edits to the same file need a merge step; permission is lost when the tab is backgrounded unless the user chose "Allow on every visit".

[R12] (effort L; impact medium) Add inline text editing on the slide for Reveal HTML only, and label generated content as not directly editable
   WHY: Path-based picking resolved 14/15 elements and the write-back touched only the intended range; Phoenix Code's interaction (double-click, Enter, Esc) is a proven model.
   RISKS: The bridge becomes a channel from untrusted deck code into the project: accept commits only during an explicit edit gesture and validate indices.

[R13] (effort S; impact low) Register WebMCP page tools behind feature detection; leave WebLLM and bring-your-own-key out
   WHY: A few hundred lines expose get_current_slide / read_file / propose_changes to agents where the origin trial or flag is on, mirroring Slidev's VS Code tools. WebLLM needs multi-gigabyte downloads; BYO-key contradicts the no-keys principle.
   RISKS: Origin-trial tokens are per origin (forks need their own) and the API has already been renamed once; write tools must only propose.

OPEN QUESTIONS:
 - Will Slidev source be compiled in the browser by another workstream? That decides whether Slidev edits can be previewed at all and whether element-level source positions can be injected at compile time (the data-line technique).
 - How often do current chat models (ChatGPT, Claude, Gemini) actually follow a requested SEARCH/REPLACE answer format? My 13 cases are synthetic; a real corpus is needed before fixing the prompt wording.
 - Should the player's 'any uncaught error is fatal' rule be relaxed for normal playback too, or only in edit mode?
 - Does the File System Access flow behave as documented end to end (picker, three-way permission prompt, FileSystemObserver on a real folder edited by VS Code)? It could not be automated in headless Chromium.
 - How do the editor and preview behave in Firefox and Safari, on a real phone keyboard and with a real screen reader? Only Chromium was available.
 - Which shipping assistants consume WebMCP page tools (Gemini in Chrome, Claude in Chrome)? Chrome's docs only name extensions and DevTools MCP.
 - Is the owner willing to register an origin-trial token (per origin, so forks would need their own) and to add a web app manifest for File Handling?
 - How should Slidev `src:` imports and disabled/hidden slides be numbered in the mapper — reimplement the frontmatter keys or ship @slidev/parser/core (33 KB gzip)?
 - How much slower are the measured reload times on a typical teacher laptop or Chromebook than on this 4-CPU container?
 - Is on-device Gemini Nano good enough for 'explain this error' or small slide-text edits? Availability was checked, quality was not.
