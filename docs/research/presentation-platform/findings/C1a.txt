##### C1a-player-origin-fidelity

SUMMARY:
I extended B1's player origin (app on 127.0.0.1:4600, player plus service worker on :4602, full Chromium 158) and tested it with unmodified Slidev builds. The tests checked rendering, keyboard navigation, a v-click step and a Vue button.

- **Mounting (Q1, Q2).** Serving each deck at its own build base on the player root works for 9/9 builds, including the default build (base "/", history router) and a /sub/deck/ build. The worker picks the deck from a ?__deck= token, which Slidev keeps across its own navigations, and from FetchEvent clientId/resultingClientId. The /d/<id>/ prefix mount plays only 2/9 builds. Rewriting the base on the fly plays 0/4.
- **Routes and two decks.** Deep links (/N, /presenter/N, /overview, /notes, /entry, ?print) work, and so does frame reload. Two decks open at once both play.
- **Kitchen-sink build (37 MB).** All 16 slides play, and Monaco plus its Web Workers report TypeScript errors even with the network blocked. Remote images, the Tweet embed, PlantUML and fonts need the network. First open takes 2.0–2.2 s.
- **Presenter (Q3).** Presenter and audience stay in sync across two frames and from a popup.
- **Reveal (Q4).** External-Markdown, ES-module, menu and chalkboard decks still play.
- **Edit loop (Q5).** Editing a Reveal deck and reloading takes a median of 82–99 ms.
- **Worker restart (Q6).** If files live only in worker memory, the deck fails after a restart ("Unknown deck"). Cache Storage, or the app re-supplying files over a MessagePort, both survive.

Two problems came up:
- **Cross-deck coupling.** Slidev's BroadcastChannel and localStorage belong to the whole player origin, so one deck's presenter drove another deck's audience view when both decks had the same title.
- **Storage partitioning.** Playwright switches Chrome's storage partitioning off by default. With it switched back on, a player on a different site from the app still plays in its frame, but the Slidev presenter popup and the Reveal speaker view break. The player must be same-site, e.g. player.qft.org next to md.qft.org.

Firefox and Safari were not tested.

FINDINGS (14):

[F1] (critical; verified-empirically) Mounting a deck at its own build base on the player-origin root, with the deck chosen per client, plays all Slidev router/base builds without touching any deck file.
   EVIDENCE: $C/out/q1-matrix.json. The 9 builds were the ordinary default build, dist-relative, and history/hash/memory x abs/rel plus history-sub. Every one passed render, ArrowRight navigation, the v-click step (hidden 2->1) and the Vue button (intensity 0.00). Root mount: 9/9. Prefix /d/<id>/: 2/9 (hash-rel, memory-rel); absolute builds fail with `404 http://127.0.0.1:4602/assets/index-BwoNhELd.js`, history ./ builds show Slidev's own 'Page /d/<id>/ not found'. Rewrite /r/<id>/ (3 regexes: "/assets/, history:X(`/`), the Vite preload helper `/`+e): 0/4; chunks load, then 'Page /1 not found'. First slide visible 106-126 ms after frame load.
   SOURCES: prototypes/C1a/player/sw.js | prototypes/C1a/scripts/q1-matrix.mjs | prototypes/C1a/out/q1-matrix.json

[F2] (critical; verified-empirically) In real Chrome (storage partitioning on), a player origin on a different site from the app breaks popups: the Slidev presenter popup returns 404, and the Reveal speaker view's previews fail. Frames still work. The player must be same-site with the app.
   EVIDENCE: Playwright disables the ThirdPartyStoragePartitioning feature by default (playwright-core coreBundle.js chromiumSwitches, issue 32230). Relaunched with the feature enabled, app on http://localhost:4600 and player on http://127.0.0.1:4602. In the frame, the Slidev deck passes every interaction and two-frame presenter sync works. The popup is top-level, so it uses the first-party partition: controlled=false, cacheKeys='', `404 http://127.0.0.1:4602/presenter/1?__deck=XS`. Reveal speaker view: popup opens, but both preview iframes fail (ERR TypeError, deck not served). Same-site with partitioning on: speaker view previews ready=true. With partitioning off, the popup wrongly works.
   SOURCES: prototypes/C1a/out/cross-site-partitioned.txt | prototypes/C1a/out/cross-site-reveal.txt | prototypes/C1a/scripts/lib.mjs | https://privacysandbox.google.com/cookies/storage-partitioning | https://github.com/microsoft/playwright/issues/32230

[F3] (critical; verified-empirically) Only Cache Storage, or the app re-supplying files on demand, survives a service-worker restart. Files held only in worker memory are lost: the open deck keeps running until it needs a file, then reload and new frames fail.
   EVIDENCE: Restart forced with CDP ServiceWorker.stopAllWorkers; a new boot timestamp confirmed it. memory: fetch from the deck 404, frame reload and new frame 'Unknown deck'; keyboard navigation inside the running deck still worked. cache (deck metadata and client map also in Cache Storage): fetch 200 via the restored clientId map, reload to /3 ok, new frame ok. ondemand (worker -> host page -> app over a transferred MessagePort): all ok, and the app answered 92 file requests.
   SOURCES: prototypes/C1a/out/q4q5q6.json | prototypes/C1a/scripts/q4q5q6.mjs

RECOMMENDATIONS (6):

[R1] (effort M; impact high) Mount each deck at its own build base on the player root, chosen per client
   WHY: Only strategy that played 9/9 Slidev builds unchanged, including the default build, plus all Reveal decks. Resolution chain: ?__deck= token on the first navigation -> persisted clientId/resultingClientId map -> Referer token -> the navigation's initiator clientId -> client URL. Navigations for missing paths fall back to index.html.
   RISKS: A deck that strips query strings and also sets no-referrer could lose its deck for popups. Several decks share one origin's storage.

[R2] (effort M; impact high) Store files in Cache Storage, with the app as source of truth answering on-demand requests over a MessagePort
   WHY: Memory-only files are lost when the worker restarts ('Unknown deck'). Cache Storage and on-demand both survived. Persist deck metadata and the client map; never rely on worker globals. Protocol: put/patch/forget/stats app->worker via a host frame pinned to the app origin; need worker->app.
   RISKS: Storage eviction and hard reload (which bypasses the worker) are untested. Cache writes for 37 MB take about 0.3 s.

[R3] (effort S; impact high) Host the player on a same-site origin (e.g. player.qft.org) and test with partitioning enabled
   WHY: With Chrome's default storage partitioning, a cross-site player breaks the Slidev presenter popup and the Reveal speaker view. Playwright disables partitioning by default, so cross-site tests need launchPartitioned() from lib.mjs.
   RISKS: GitHub Pages needs a custom subdomain for a second origin. A same-site sibling shares cookies scoped to qft.org.

[R4] (effort S; impact medium) Play one deck at a time per player origin, or clear slidev-* state when switching decks
   WHY: A different deck with the same title drove another deck's audience view through Slidev's per-origin BroadcastChannel and localStorage. Isolating decks that are open at the same time would need separate origins.
   RISKS: Clearing localStorage resets Slidev's drawings and presenter preferences.

[R5] (effort S; impact medium) Edit loop: patch the file in the store, then navigate the frame with a cache-busting query plus the current route
   WHY: 82-99 ms median round trip for Reveal, 176 ms for a Slidev reload. Fast enough for edit-and-preview without hot reload.
   RISKS: Slidev source edits still need an in-browser compiler (B2). Reveal decks without hash:true lose the slide position unless the app tracks it via the postMessage API.

[R6] (effort S; impact low) Move unzip off the main thread and avoid duplicate copies for large decks
   WHY: For the 37 MB build, sync fflate takes 356-408 ms on the main thread and the app keeps a second copy of every file. Browser memory reached about 1.1-1.2 GB after the first slide.
   RISKS: Worker-based unzip needs a same-origin worker script on the app's CSP (B2 F5 shows this is allowed).

OPEN QUESTIONS:
 - Firefox and Safari behaviour was not tested: service worker control of sandboxed allow-same-origin iframes, how each partitions popups opened from a same-site iframe, and BroadcastChannel across frame and popup.
 - Idle termination by the browser (about 30 s in Chromium) and storage eviction were not tested; the restart was simulated with CDP stopAllWorkers.
 - Shift-reload of a deck frame bypasses the worker and hits the player's static server (404). Could a 404.html bootstrap on Pages recover?
 - Security on the player origin was not evaluated: cross-deck storage reads, exfiltration through popups or self-navigation, and the A1 prerender/WebRTC leaks under the worker's CSP.
 - Why the template's Mermaid slide renders no SVG (also under plain HTTP in B2).
 - Whether a deck that sets Referrer-Policy no-referrer and drops query strings still resolves for popups; the initiator-clientId fallback was confirmed only for reloads.
