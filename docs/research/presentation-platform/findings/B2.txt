##### B2-slidev

SUMMARY:
Slidev 53.1.0 is a Vite application: Markdown is compiled to Vue in Node by 22 plugins, and there is no official Node-less or in-browser mode (sli.dev/new is StackBlitz).

An ordinary `slidev build` cannot be opened from a ZIP as-is: it fails on file://, in a blob: document, in an opaque-origin sandbox and, with the default base, on a sub-path. Each failure has a mechanical cause.

Two routes were prototyped and verified in Chromium 158 against a replica of the md.qft.org player:

- **Play built decks.** Six textual patches plus bundling turn an ordinary build into a single HTML the current sandbox plays. It worked for 7 router/base variants, and entirely in the browser with esbuild-wasm in a same-origin Worker under the site's present CSP (0.7–1.7 s). Decks using Monaco are not covered.
- **Edit source and re-render without Node.** A prebuilt generic Slidev client plus a 708 KB (gzip) in-browser compiler that bundles upstream parser and markdown plugins. Output was DOM- and pixel-identical to the real build for a 5-slide deck, 5/5 slides on a richer deck, and 7/16 on the official kitchen-sink template. Compile takes 0.07–1.4 s with no eval or WebAssembly.

Out of reach without Node or network: npm themes, addons and dependencies, vite/setup/uno config files, Monaco, TwoSlash, remote embeds; icons need bundled data.

Today's player kills a deck on any CSP violation or unhandled rejection, and Slidev's defaults trigger both (Wake Lock; the official template's remote cover image).

Firefox and Safari were not tested.

RECOMMENDATIONS (8):

[R1] (effort M; impact high) Accept ordinary Slidev build ZIPs by converting them in the browser
   WHY: This is what an AI agent with a shell produces when it follows the official skill. The conversion (six patches plus bundling) was verified for 7 router/base variants and runs fully client-side in under 2 s with esbuild-wasm in a same-origin Worker, without touching the sandbox policy. Fidelity is that of the real build. Replace the current 'website build ZIP' rejection with this path.
   RISKS: Two patches are regexes over minified output and were only tested on 53.1.0 builds. Decks with Monaco fail (non-static imports, workers, tens of MB) and need a clear message. Asset URLs resolved at runtime (frontmatter backgrounds, component props) are not covered. First use downloads a 3.6 MB (gzip) wasm file.

[R2] (effort S; impact high) Stop treating every CSP violation and unhandled rejection as fatal
   WHY: Slidev's defaults trigger both: the Wake Lock request rejects in the sandbox, and the official template's first slide loads a remote image. Remove `navigator.wakeLock` before the deck starts, keep script and connect violations fatal, and downgrade image/font/media violations to a visible notice.
   RISKS: Less strict failure signalling; a deck with many blocked images looks broken without explanation unless the notice is clear.

[R3] (effort S; impact high) Classify uploads before choosing a path
   WHY: A 113-line classifier distinguished Slidev source, Slidev build (with version, base, router mode, Monaco/worker/external-script flags), the site's own formats, reveal.js, Marp and plain Markdown in 17/17 fixtures. It lets the site route builds to conversion, sources to editing, and tell the user exactly which feature blocks a deck instead of a generic rejection.
   RISKS: Router-mode detection reads minified code and is a hint only; builds older than 0.49.0 lack the version meta.

[R4] (effort S; impact medium) Offer structured slide editing on the upstream parser first
   WHY: @slidev/parser/core is browser-safe at 36 KB gzip and provides parse, prettify and stringify, the same primitives the built-in MCP server uses. Listing, reordering, inserting, deleting slides and editing Markdown, notes and frontmatter can be written back into the ZIP with zero compatibility drift, independent of whether a preview exists.
   RISKS: Without a preview, users cannot see the effect of an edit until the deck is rebuilt elsewhere.

[R5] (effort L; impact high) Build the generic-client plus in-browser compiler as a labelled preview tier
   WHY: It is the only route that shows edits without Node. The prototype reached DOM- and pixel-identical output on simple decks with about 430 lines, because it bundles upstream code rather than copying it. Gate it on the classifier's blocker list (non-default theme, addons, Monaco, npm dependencies, config files) and fall back to the build-conversion path otherwise.
   RISKS: Hooks into non-public Slidev internals and must be rebuilt and diff-tested per Slidev release. Themes need prebuilt packs or network access. Partial compatibility can mislead users if unsupported features degrade silently.

[R6] (effort S; impact medium) Rewrite the site's instructions for AI tools around what was measured
   WHY: Ask for `slidev build --router-mode memory --base ./` (Slidev >= 52.17), `wakeLock: false`, `fonts.provider: none`, images in `public/` rather than remote URLs, no Monaco, Tweet or PlantUML, and a ZIP containing both `dist/` and the source. The official skill predates memory mode and recommends absolute bases.
   RISKS: Agents and users will often ignore instructions, so this complements the conversion path rather than replacing it.

[R7] (effort S; impact medium) Run wasm or eval-dependent tooling in same-origin Workers instead of loosening the page CSP
   WHY: Measured in Chromium 158: a Worker loaded from the site's own URL may compile WebAssembly and evaluate code while the page keeps `script-src 'self'`. This is what allows esbuild-wasm today and would allow heavier compilers later.
   RISKS: Only verified in Chromium; Firefox and Safari follow the same documented rule but were not run. A CSP response header added later (other hosting) would change this.

[R8] (effort S; impact medium) Do not pursue running the real Slidev toolchain in the browser for now
   WHY: The toolchain is 111 MB of tarballs and 494 MB on disk, the official template build peaked near 2.6 GB RSS natively, WebContainers need cross-origin isolation headers GitHub Pages cannot send, and packages would be fetched from the network on every project.
   RISKS: Leaves Monaco, TwoSlash, npm-theme and config-file decks dependent on an external rebuild.
