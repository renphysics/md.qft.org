##### C2-platform-facts

SUMMARY:
I checked F1-F8 against primary sources: GitHub, Chromium, WebKit, MDN and MDN browser-compat-data 8.1.11 (dated today), Cloudflare, Bugzilla and the README files. I also ran two small tests in full Chromium 158. Test X1: an infinite loop in a same-site subdomain iframe freezes the embedding page. It stops freezing only when the subdomain sends Origin-Agent-Cluster: ?1 over HTTPS, and GitHub Pages cannot send that header. Cross-site frames and opaque sandboxed frames run in their own process, so they do not freeze the editor. Test X2: once storage partitioning is enabled, a cross-site iframe gets a working partitioned service worker, IndexedDB and Cache Storage even when third-party cookies are blocked. A same-site subdomain frame gets unpartitioned storage. Caution: Playwright's default Chromium launch disables ThirdPartyStoragePartitioning. My first X2 run therefore showed cross-site storage being denied, which is legacy behaviour. Any earlier cross-site storage result needs re-checking with that flag removed. GitHub Pages sends no security headers (cache-control is max-age=600). github.io is on the Public Suffix List, and renphysics.github.io/md.qft.org/ redirects (301) to md.qft.org. The git history shows the Cloudflare-to-Pages move came with a commit titled 'MIT reuse' that adds automatic fork URLs; that this was the motive is my inference. Running Slidev's Node tooling in the browser through WebContainers is not realistic: there are licence terms, COOP/COEP headers are required, and it is really Chromium-only. An earlier run took about 52 s and 83 MB before the first slide. Recommendation: put the player on a cross-site origin (a second repository at renphysics.github.io/<repo>/) rather than play.qft.org. Forks without a second origin should keep using the opaque Tier-1 sandbox.

FINDINGS (15):

[F1] (critical; verified-empirically) An infinite loop in a same-site subdomain iframe (play.qft.* inside md.qft.*) freezes the editor in Chrome desktop. Explicit Origin-Agent-Cluster: ?1 over HTTPS prevents the freeze, but GitHub Pages cannot send that header. Cross-site frames and opaque sandboxed frames (allow-scripts only) do not freeze the parent.
   EVIDENCE: scripts/freeze-https.mjs in Chromium 158.0.8127.36 with channel 'chromium'. The parent counts setInterval ticks while the child runs for(;;){}. Results: same-origin FROZEN; same-site subdomain FROZEN; subdomain with OAC ?1 responsive (ticks 8->38); cross-site responsive; opaque srcdoc sandbox responsive. Over plain HTTP the OAC header had no effect. Chromium's documentation says OAC is 'not a security guarantee' and that 'Since 127.0.6483.0, Desktop Chromium moves [sandboxed opaque] documents into a separate process'. On Android this happens only with partial Site Isolation.
   SOURCES: https://chromium.googlesource.com/chromium/src/+/main/docs/process_model_and_site_isolation.md | https://www.chromium.org/Home/chromium-security/site-isolation/

[F2] (critical; verified-empirically) With storage partitioning enabled (the Chrome 115+ default), a cross-site player iframe can register a service worker and use IndexedDB and Cache Storage even when third-party cookies are blocked (the Incognito default). Its storage is partitioned. A same-site subdomain frame is unpartitioned. Playwright's default Chromium launch disables ThirdPartyStoragePartitioning, and in that state cross-site frames with 3PC blocked are denied ('The user denied permission to use Service Worker.').
   EVIDENCE: scripts/sw3p-real.mjs removes Playwright's --disable-features list via ignoreDefaultArgs. With 3PC blocked (profile pref cookie_controls_mode=1): cross-site iframe sw registered, idb ok, cache ok, localStorage written at top level reads as null (partitioned), hasStorageAccess false. Same-site iframe reads the top-level value. A cross-site popup is first-party. Chrome docs: 'enabled for all users on Chrome 115 and later'; 'Service Workers registered from a third-party context are now partitioned.' Google (2025-04-22): Incognito 'already blocks third-party cookies by default'.
   SOURCES: https://privacysandbox.google.com/cookies/storage-partitioning | https://privacysandbox.google.com/blog/privacy-sandbox-next-steps

[F4] (high; verified-primary-source) There are two second-origin options. (1) A second repository at https://renphysics.github.io/<repo>/: the user site renphysics.github.io does not exist, so project sites without a custom domain are served there. (2) The same repository with a custom subdomain such as play.qft.org (CNAME to renphysics.github.io). github.io is in the PRIVATE section of the Public Suffix List (version 2026-11-23), so renphysics.github.io is its own site, cross-site to qft.org. Every github.io user is cross-site to every other.

[F5] (medium; verified-primary-source) Service workers work on Pages under project sub-paths: JupyterLite registers scope https://jupyterlite.github.io/demo/. The HTTP max-age=600 does not delay service-worker script updates, because Chrome 68+ and others ignore HTTP caching for the SW script by default (updateViaCache 'imports'). importScripts and app files can still be up to 10 minutes stale unless their URLs are versioned. Widening a SW's scope above its directory needs Service-Worker-Allowed, which Pages cannot send.
   EVIDENCE: web.dev: 'Most browsers, including Chrome 68 and later, default to ignoring caching headers when checking for updates of the registered service worker script. They still respect caching headers when fetching resources loaded inside a service worker via importScripts().' MDN: updateViaCache default 'imports'. BCD: Chrome 68, Firefox 57, Safari 11.1. The JupyterLite registration comes from the earlier B8 probe (out/jupyterlite.json).
   SOURCES: https://web.dev/articles/service-worker-lifecycle | https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/updateViaCache

[F6] (medium; verified-primary-source) Firefox: State Partitioning has been on by default since Firefox 103 and covers Service Workers, DOM Cache and IndexedDB, keyed by (origin, top-level site). Partitioned third-party service workers landed in bug 1731999 (FIXED, 96 branch). The pref no longer exists, so the behaviour is unconditional. The exact release where this reached all users is not confirmed. In private windows navigator.serviceWorker was undefined before Firefox 139.
   EVIDENCE: MDN (modified 2026-06-15): 'From Firefox 103, State Partitioning is turned on by default.' 'Firefox double-keys all client-side state by the origin of the resource being loaded and by the top-level site.' Bugzilla REST: 1731999 'Enable partitioned service worker for third-party contexts in dFPI' resolved 2021-11-30; meta 1730885 closed 2022-10-26. firefox.js: pref("network.cookie.cookieBehavior", 5). BCD note on Navigator.serviceWorker about Firefox 139.
   SOURCES: https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/State_Partitioning | https://bugzilla.mozilla.org/show_bug.cgi?id=1731999 | https://raw.githubusercontent.com/mozilla-firefox/firefox/main/browser/app/profile/firefox.js

[F7] (high; verified-primary-source) Safari partitions third-party service workers and their storage. It also makes third-party localStorage and IndexedDB ephemeral. A cross-origin frame gets 10% of the main frame's origin quota. Whether same-site cross-origin frames are also partitioned is unclear, and so is whether third-party SW caches are ephemeral.
   EVIDENCE: webkit.org/tracking-prevention: 'Third-party LocalStorage and IndexedDB are partitioned per first-party website and also made ephemeral.' 'Third-party Service Workers are partitioned and their cache and IndexedDB is partitioned too.' WebKit blog (2023-08-10): 'A cross-origin frame uses a different storage partition ... The quota is currently 10% of the main frame's origin quota.' Not tested: no WebKit engine here.
   SOURCES: https://webkit.org/tracking-prevention/ | https://webkit.org/blog/14403/updates-to-storage-policy/

[F8] (high; verified-primary-source) Process isolation by browser. Chrome desktop isolates per site (eTLD+1) since Chrome 67. On Android it needs at least 2 GB RAM and covers only login/OAuth/COOP sites. Origin-Agent-Cluster has defaulted to ?1 since Chrome 115, but that default does not create a separate process. Firefox Fission is on by default on desktop (since Firefox 95 per secondary sources; fission.autostart true) and off in Android Release. Safari has a site-isolation design in WebKit, but no Safari 26.x/27.x release note says it has shipped.
   EVIDENCE: chromium.org: 'a site: the scheme and registered domain name ... ignoring subdomains'; 'enabled by default for all sites in Chrome 67'; 'On Android devices with at least 2 GB of RAM, Site Isolation has been enabled for sites that users log into since Chrome 77'. BCD note: 'Since Chrome 115, the default value of this header changed from ?0 to ?1.' StaticPrefList.yaml fission.autostart: true. docs.webkit.org SiteIsolation page. I grepped Apple release-notes JSON for 26, 26.2, 26.4, 27 and 27.1-27.3 and found no mention of site isolation. The Safari status is inferred.
   SOURCES: https://www.chromium.org/Home/chromium-security/site-isolation/ | https://wiki.mozilla.org/Project_Fission | https://docs.webkit.org/Deep%20Dive/SiteIsolation.html | https://developer.apple.com/documentation/safari-release-notes/safari-27_3-release-notes

[F9] (high; verified-primary-source) Storage quotas. Chromium: up to 60% of disk per origin, in best-effort and persistent mode alike. Firefox best-effort: min(10% of disk, 10 GiB per eTLD+1 group); persistent: 50% of disk, capped at 8 TiB. Safari browser app: about 60% per origin and 80% overall; home-screen apps get the same. Eviction removes a whole origin at once. persist(): Firefox shows a prompt; Chrome and Safari decide by heuristics (WebKit favours home-screen apps). OPFS is available in Chrome 86, Firefox 111 and Safari 15.2.
   EVIDENCE: MDN quotas page (modified 2026-01-05): 'an origin can store up to 60% of the total disk size in both persistent and best-effort modes'; 'In Firefox, when a site chooses to use persistent storage, the user is notified with a UI popup'; 'all of its data, not parts of it, is deleted at the same time'. WebKit: 'grants a request based on heuristics like whether the website is opened as a Home Screen Web App.' BCD getDirectory: Chrome 86, Firefox 111, Safari 15.2.
   SOURCES: https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria | https://webkit.org/blog/14403/updates-to-storage-policy/

[F10] (high; verified-primary-source) Safari deletes all script-writable storage after 7 days of Safari use without user interaction on the site. Home-screen web apps are exempt.
   EVIDENCE: WebKit 2020-03-24: 'deleting all of a website's script-writable storage after seven days of Safari use without user interaction on the site' ... 'Web applications added to the home screen are not part of Safari and thus have their own counter of days of use ... We do not expect the first-party in such a web application to have its website data deleted.' tracking-prevention page: 'The first-party domain of home screen web applications is exempt from ITP's 7-day cap'.
   SOURCES: https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/ | https://webkit.org/tracking-prevention/

RECOMMENDATIONS (6):

[R1] (effort M; impact high) Host the player on a cross-site origin: a second repository published at https://renphysics.github.io/<player-repo>/
   WHY: On desktop Chrome (X1) and Firefox it gets its own renderer process, so a looping or hostile deck cannot freeze the editor or sit in its address space. It cannot set or receive qft.org cookies. In Chrome 158 the service worker and Cache Storage keep working in the frame, partitioned, even with third-party cookies blocked (X2). Partitioning is harmless because the editor re-supplies the files each session.
   RISKS: Safari makes third-party IndexedDB/localStorage ephemeral and has no shipped site isolation. Android Chrome often shares the process. Every renphysics project site shares that origin, so keep nothing else there. Brave, Firefox and Safari behaviour was not tested here.

[R2] (effort S; impact high) Do not use play.qft.org on GitHub Pages unless the host can send Origin-Agent-Cluster: ?1
   WHY: A same-site subdomain shares the editor's renderer process when the OAC header is absent; X1 froze the parent. It can also set Domain=qft.org cookies. Behind Cloudflare with a _headers file sending OAC ?1, the freeze went away in X1, though Chromium calls OAC only a hint.
   RISKS: Cloudflare hosting for the player only would split the deployment and weaken the 'forkable on Pages alone' story.

[R3] (effort S; impact medium) Offer 'present in new tab' on the player origin
   WHY: A cross-site top-level window opened with window.open (files sent by postMessage) gets first-party storage and its own process. It worked with third-party cookies blocked (X2 popup case).
   RISKS: Pop-up blockers need a user gesture. postMessage needs the opener reference, so do not use noopener.

[R4] (effort S; impact high) Forks degrade to Tier 1 by configuration
   WHY: Make the player origin a build-time setting. When it is empty, hide 'run unmodified deck' and keep the opaque-sandbox inliner, offering ZIP download or local opening for decks Tier 1 cannot run. A fork can point the setting at its own <user>.github.io/<player-repo>/. Never fall back to allow-same-origin on the app origin.
   RISKS: Feature differences between the main site and forks must be documented.

[R5] (effort S; impact medium) Re-run cross-site storage tests with storage partitioning enabled
   WHY: Playwright's default Chromium args include --disable-features=...ThirdPartyStoragePartitioning..., so default-launch tests measure pre-2023 storage behaviour. Pass ignoreDefaultArgs with the default --disable-features string, then your own list without that feature (see scripts/sw3p-real.mjs).
   RISKS: Results from B1 and C1a for cross-site frames may change.

[R6] (effort S; impact medium) Ship prebuilt Slidev dist (hash router, base ./) instead of building in the browser
   WHY: WebContainers is Chromium-first and needs COOP/COEP plus licence terms. A cold start took about 52 s and 83 MB through StackBlitz's CDN, and that sends data off the device, which conflicts with the 'processed locally' promise.
   RISKS: Users must build Slidev decks locally or with an AI tool before uploading.

OPEN QUESTIONS:
 - Firefox and Safari were not tested here. Does a partitioned service worker in a cross-site iframe control the frame's subresource fetches in Safari 27, and is its Cache Storage ephemeral?
 - Does WebKit partition storage of same-site cross-origin frames such as play.qft.org inside md.qft.org? The WebKit blog says 'cross-origin frame'.
 - Which Firefox release first shipped partitioned third-party service workers to all users? Bug 1731999 is fixed on the 96 branch, but the shipping release was not confirmed.
 - Has Safari shipped site isolation by default? No Safari 26.x/27.x release note mentions it, and WebKit bugs from 2026 show the work is still in progress.
 - Does Brave (or Chrome with stricter settings) block partitioned third-party service workers? The WebContainers documentation suggests it does.
 - Were B1 and C1a player-origin tests run with Playwright's default ThirdPartyStoragePartitioning disable? Their cross-site storage results should be re-checked.
 - Is Nodebox/Sandpack still maintained in 2026? github.com was unreachable, so this was not checked.
 - Does qft.org (Cloudflare-hosted) rely on any cookie-authenticated endpoints? That decides how much cookie risk a same-site play.qft.org would add.
