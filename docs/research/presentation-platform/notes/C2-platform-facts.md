## Two new experiments (full Chromium 158.0.8127.36, chromium.launch({channel:'chromium'}), HTTPS, hosts mapped to 127.0.0.1)

### X1 Does `for(;;){}` in an iframe freeze the embedding page? (scripts/freeze-https.mjs, port 4651)
Parent md.qft.test has a 50 ms setInterval counter; child loops after 300 ms.
```
same-origin                                   PARENT FROZEN
same-site subdomain (play.qft.test)           PARENT FROZEN
same-site subdomain + Origin-Agent-Cluster:?1 parent responsive (ticks 8 -> 38)
same-site subdomain, parent also OAC          parent responsive
cross-site (renphysics.github-io.test)        parent responsive
opaque sandbox srcdoc (allow-scripts only)    parent responsive
```
Over plain HTTP the OAC header had no effect (frozen) - OAC is only honoured in secure contexts.
GitHub Pages cannot send Origin-Agent-Cluster, and an OAC meta tag does not exist -> on Pages a play.qft.org frame shares the editor's renderer process [E + I].

### X2 Service worker / IndexedDB / Cache Storage / localStorage in an iframe (scripts/sw3p-real.mjs, port 4653)
WARNING for all agents: Playwright's default Chromium args include `--disable-features=...ThirdPartyStoragePartitioning...` (seen in `ps`), i.e. storage partitioning is OFF in default Playwright launches. sw3p-real.mjs removes it via ignoreDefaultArgs. A first run without that fix (sw3p-block.mjs) wrongly showed cross-site frames denied SW/IDB/Cache/localStorage ("The user denied permission to use Service Worker.") when 3PC were blocked - that is the pre-partitioning legacy behaviour, not real Chrome.
Real-config results (top-level visits first wrote localStorage 'a'='top-level' on both player hosts; lsBefore shows what the frame sees):
```
3PC allowed  same-site subdomain iframe  sw registered, idb ok, cache ok, lsBefore "top-level" (unpartitioned), hasStorageAccess true
3PC allowed  cross-site iframe           sw registered, idb ok, cache ok, lsBefore null (partitioned)
3PC allowed  cross-site popup            sw registered, ..., lsBefore "top-level" (first-party)
3PC blocked  same-site subdomain iframe  same as allowed
3PC blocked  cross-site iframe           sw registered, idb ok, cache ok, lsBefore null, hasStorageAccess false
3PC blocked  cross-site popup            first-party, all ok
```
(3PC blocked = profile pref cookie_controls_mode=1, the Chrome Incognito default; --test-third-party-cookie-phaseout had no effect in 158.)
=> In Chrome 158 a cross-site player iframe gets a working partitioned SW + storage even with 3PC blocked [E]. Same-site subdomain frames are unpartitioned [E]. Not tested: Brave (WebContainers docs say its blocking "tends to stop WebContainers from running"), Firefox, Safari.

## F2 Storage / SW in iframes
- Chrome [P]: https://privacysandbox.google.com/cookies/storage-partitioning (last updated 2025-06-13): "The feature has been enabled for all users on Chrome 115 and later." Data is "only available to contexts that share both the same origin and the same top-level site." "Service Workers registered from a third-party context are now partitioned." Ancestor bit: chain of only same-site frames "remains shared". Blob URLs partitioned since Chrome 137. Same-site subdomain frame (play.qft.org in md.qft.org) = key (play.qft.org, top-level site qft.org) = same as visiting play.qft.org directly -> unpartitioned [P+I]. With partitioning enabled, blocking third-party cookies does not remove SW/IDB/Cache from cross-site frames [E, X2].
- Firefox [P]: MDN State Partitioning (modified 2026-06-15): "From Firefox 103, State Partitioning is turned on by default." Partitioned APIs list includes DOM Cache, IndexedDB, Broadcast Channel, Shared Workers, Service Workers. "Firefox double-keys all client-side state by the origin of the resource being loaded and by the top-level site." Bugzilla 1731999 "Enable partitioned service worker for third-party contexts in dFPI" RESOLVED FIXED, 96 Branch (2021-11-30); meta 1730885 "Enable Service Worker in dFPI" closed 2022-10-26; the pref privacy.partition.serviceWorkers no longer exists in current StaticPrefList.yaml (so on unconditionally) [P; exact release version that shipped it U]. firefox.js: `pref("network.cookie.cookieBehavior", 5)` (dFPI default) [P]. BCD: "Before Firefox 139, the serviceWorker object is undefined in private windows." Same-site subdomain: keyed by top-level site qft.org -> first-party [I from MDN definition].
- Safari [P]: https://webkit.org/tracking-prevention/ : "Third-party LocalStorage and IndexedDB are partitioned per first-party website and also made ephemeral." "Third-party Service Workers are partitioned and their cache and IndexedDB is partitioned too." WebKit storage policy (2023-08-10, https://webkit.org/blog/14403/updates-to-storage-policy/): "A cross-origin frame uses a different storage partition than the frame it is embedded in ... The quota is currently 10% of the main frame's origin quota." Whether WebKit treats a same-site cross-origin frame as partitioned is [U] (the blog says "cross-origin"); whether a partitioned third-party SW's Cache Storage is ephemeral is [U]. Private Browsing: "uses a new ephemeral session for each tab".

## F3 Process isolation
- Chrome desktop: per site, not per origin [P]: chromium.org Site Isolation: "a site: the scheme and registered domain name ... ignoring subdomains"; "Site Isolation was enabled by default for all sites in Chrome 67 on Windows, Mac, Linux, and Chrome OS"; Android: "On Android devices with at least 2 GB of RAM, Site Isolation has been enabled for sites that users log into since Chrome 77" (Chrome 92 adds OAuth and COOP sites). process_model_and_site_isolation.md: Android <2 GB RAM: Site Isolation disabled; "Since 127.0.6483.0, Desktop Chromium moves these [sandboxed, no allow-same-origin] documents into a separate process from their parent or opener. On Android, these documents will only be in a separate process if their parent/opener uses Partial Site Isolation."
- Origin-Agent-Cluster [P+E]: BCD note "Since Chrome 115, the default value of this header changed from ?0 to ?1." (Firefox 138, Safari 27.3 support the header). Chromium doc: OAC header is "a hint ... that an origin locked process can be used. This is not a security guarantee". Default-OAC does NOT give a process: X1 shows the same-site subdomain freezes the parent unless the explicit header is sent over HTTPS.
- Firefox: Fission (site-per-process) on desktop since Firefox 95 [S: wiki.mozilla.org/Project_Fission, ghacks]; `fission.autostart: true` in StaticPrefList.yaml [P]; Android: Fission architecture present but off in Release [S: connect.mozilla.org post].
- Safari: WebKit has a Site Isolation design (docs.webkit.org "Site isolation puts content from different Sites into different processes", Site = protocol+eTLD+1) and many 2026 bugs; no Safari 26.x/27.x release note mentions site isolation shipping (checked Apple release-notes JSON for 26, 26.2, 26.4, 27, 27.1-27.3) -> treat as not shipped by default [U/I].
- Conclusion "infinite loop in frame freezes embedder?":
  | frame | Chrome desktop | Chrome Android | Firefox desktop | Firefox Android | Safari |
  |---|---|---|---|---|---|
  | (a) opaque sandbox (same-site) | no (since 127) [E] | yes unless partial SI [P] | yes, likely (Fission is per site; opaque frames not documented as isolated) [U] | yes [I] | yes [I] |
  | (b) same-site subdomain, no OAC header (Pages) | yes [E] | yes [I] | yes (same site) [I] | yes [I] | yes [I] |
  | (c) cross-site (github.io) | no [E] | often yes (only login/COOP sites isolated) [P] | no (Fission) [I] | yes [I] | yes, until site isolation ships [U] |
  So a watchdog (MessageChannel heartbeat + "stop deck" that removes the iframe) works only where the frame is out of process; where it is in-process, nothing in the page can recover - the browser's "page unresponsive" dialog is the only escape.

## F4 Storage quotas / eviction / persist / OPFS
- MDN Storage quotas and eviction criteria (modified 2026-01-05) [P]: Chromium: "an origin can store up to 60% of the total disk size in both persistent and best-effort modes." Firefox best-effort: min(10% of disk, 10 GiB group limit per site [eTLD+1]); persistent: "up to 50% of the total disk size, capped at 8 TiB". Safari browser app: "each origin can store up to around 60% of total disk"; other WebKit apps ~15%; Home Screen/Dock web app same as browser. Eviction: whole origin at once ("all of its data, not parts of it, is deleted at the same time"), LRU under storage pressure; "Proactively, for origins that aren't used regularly, which happens only in Safari": "If an origin has no user interaction ... in the last seven days of browser use, its data created from script will be deleted." persist(): "In Firefox ... the user is notified with a UI popup"; "Safari and most Chromium-based browsers ... automatically approve or deny the request based on the user's history of interaction". Private browsing: "stored data is usually deleted when the private browsing mode ends."
- WebKit [P]: overall quota 80% of disk (browser app); "WebKit currently grants a request [persist()] based on heuristics like whether the website is opened as a Home Screen Web App." Persistent mode excludes the origin from eviction.
- 7-day cap and installed-app exemption [P]: webkit.org/blog/10218 (2020-03-24): "deleting all of a website's script-writable storage after seven days of Safari use without user interaction on the site" ... "Web applications added to the home screen are not part of Safari and thus have their own counter of days of use ... We do not expect the first-party in such a web application to have its website data deleted." tracking-prevention page: "The first-party domain of home screen web applications is exempt from ITP's 7-day cap on all script-writeable storage".
- BCD 8.1.11 [P]: StorageManager.persist Chrome 55 / Firefox 57 / Safari 15.2; estimate Safari 17; getDirectory (OPFS) Chrome 86 (Android 109) / Firefox 111 / Safari 15.2; createSyncAccessHandle Chrome 102 / Firefox 111 / Safari 15.2.

## Recommendation (for the orchestrator)
- Prefer a cross-site player origin: a second repository published at https://renphysics.github.io/<repo>/ (or any github.io / separate registrable domain). Reasons: own renderer process on desktop Chrome (X1) and Firefox (Fission), so a hostile or looping deck cannot freeze or Spectre-read the editor; no cookie reach into qft.org; SW + Cache Storage work in the frame in Chrome even with 3PC blocked (X2, partitioned). Costs: partitioned storage (keyed by top-level site, fine because the editor re-supplies files), Safari makes third-party IDB/localStorage ephemeral and has no site isolation, Android Chrome often shares the process anyway; all project sites of renphysics share that origin (keep only the player there).
- play.qft.org (same-site custom subdomain) is the weaker choice on GitHub Pages: unpartitioned and simple, but it shares the editor's process because Pages cannot send Origin-Agent-Cluster (X1: frozen without the header, responsive with it), and it can set Domain=qft.org cookies / receive SameSite cookies of qft.org. It becomes a good choice only on a host that can send `Origin-Agent-Cluster: ?1` (e.g. Cloudflare _headers, which qft.org already uses) - and even then OAC is "not a security guarantee".
- Optional: open the player as a top-level tab/popup on the cross-site origin for "present" mode (first-party storage, own process) [E].
- Forks without a second origin degrade to Tier 1 (opaque sandbox, inlined decks, network-free), with the player-origin URL as a build-time setting (empty = feature hidden; show "download ZIP / open locally" for decks Tier 1 cannot run). Never run decks with allow-same-origin on the app origin (A1 exp9). A fork may point its setting at its own <user>.github.io/<player-repo>/.
